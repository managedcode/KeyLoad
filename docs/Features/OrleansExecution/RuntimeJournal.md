# OrleansExecution: replicated runtime journal

Decision: [ADR-110](../../ADR/ADR-110-orleans-execution-primitives.md); cluster concept: [ADR-136](../../ADR/ADR-136-orleans-partition-ownership.md). Related: [runtime adoption](RuntimeAdoption.md), [journal lifetime](RuntimeJournalLifetime.md), REQ/AC-ORL-013.

## Authority and execution

KeyLoad uses the Orleans Journaling and DurableJobs APIs from the centrally pinned packages with the explicit `orleans-binary` journal format. A named KeyLoad provider implements the storage and catalog interfaces. Every journal read and write is a freshly signed request through the connection grain's CQRS stream (`IConnectionGrain.ExecuteStreamAsync`). The silo-local ZoneTree owner applies the canonical records; writes are replicated through ordinary Orleans calls to the ZoneTree owners on `ReplicaCount` silos and acknowledged after every configured copy confirms durable local apply. No provider commits storage directly.

The journal is internal infrastructure state, distinct from logical user partitions. A protected persisted `keyload-internal-runtime-journal` identity has no public credentials, user grants, administrator role or SchedulerManage, and can execute only the closed journal commands and reads. A private identity-creation command, run under a freshly revalidated persisted administrator, creates it; a missing or inconsistent identity afterwards is a recovery failure. Public principal/API-key changes and normal request purposes cannot configure or invoke this identity. Journal metadata authority never authorizes saga effects, which use the persisted creator.

```mermaid
flowchart LR
  Due[StatelessWorker due batch] --> Jobs[DurableJobs]
  Jobs --> Journal[Journaling provider]
  Journal --> Conn[Request envelope via connection grain]
  Conn --> Owner[Silo-local ZoneTree owner]
  Owner --> Copies[Every configured copy acknowledges]
  Jobs --> Handler[Job handler reloads saga and creator]
  Handler --> Conn
```

## Canonical storage contract

One internal `RuntimeJournal` OperationKind is appended without renumbering existing values. Its generated mutation has closed actions for identity creation, Create, UpdateMetadata, Append, Replace and Delete. Private reads return a header, one bounded opaque byte page or the complete bounded journal catalog. No public SDK/MCP tool, SQL opcode or parallel dispatcher is introduced. Generated header/chunk/capacity records use stable v1 aliases and field IDs. Exact user content, the storage codec and recovery journals keep their current contracts. The private journal key family uses a version-1 marker under the sole current format in [CurrentFormat](../StorageRecovery/CurrentFormat.md).

The canonical silo-local store carries a store identity whose minimum reader contract is `StoreReaderContract.RuntimeJournal`. Startup validates the store before recovery or silo admission without modifying that identity. Missing, zero or unknown capabilities and unsupported identity magic are rejected before any file mutation. Checkpoint, backup, restore and reopen preserve the required capability, and installing a snapshot into a non-current store is rejected. A physically absent field decodes as unsupported and never inherits a permissive default. No alternate reader, automatic promotion or conversion exists.

Each journal has a nonempty instance GUID, owner generation, independent content revision and metadata ETag. Create is atomic and idempotent; delete and recreate produce a new instance. Append, replace and delete compare the captured instance, owner generation and content revision under the atomic apply gate. Metadata writes use full ETag compare-and-swap, and mismatches return null through the metadata API. An explicitly null metadata ETag keeps the unconditional-update contract under the same gate and never revalidates a stale content writer. Metadata reads return a fresh snapshot without replacing the captured version, and content version mismatches map to execution `InconsistentStateException`.

Changes to the tagged execution `DurableJobsOwner` property, including release, reclaim and poison transitions, increment owner generation. Same-owner `DurableJobsClosed`, adoption bookkeeping and format updates do not invalidate the current writer. Every successful content write advances its captured revision, so an old handle cannot refresh itself into a new owner. Reads pin the header and content revision across bounded pages and fail on change. One ArcBufferWriter retains incomplete binary entries across page boundaries until the consumer reports completion, bounded by journal capacity. Stable command identity resolves unknown write outcomes through existing receipts.

payload bytes stay opaque and never use JSON fallback. The centrally validated `RuntimeJournalOptions` admits at most 32 journals, 2 MiB per journal, 64 MiB total data, 64 KiB chunks/read pages and 8 KiB UTF-8 metadata per journal; journal names and metadata keys/values have explicit byte limits. Admission and catalog reads enforce these limits on committed state, not only on callers. The provider owns a bounded striped asynchronous gate set sized by the validated maximum journal count. Handles for the same journal borrow the same gate and each keeps its own captured instance, owner generation and content revision. Execution `IJournalStorage` has no disposal contract, so handles never allocate an owned disposable gate; provider disposal follows shutdown and joined work and idempotently releases the gate set. The catalog materializes all selected entries before its claim budget, so the provider returns the whole bounded catalog or a terminal error and never a truncated one. Delete releases capacity atomically.

## Startup and shutdown

startup begins journal catalog discovery without awaiting it; asynchronous provider calls await a separate cancellable readiness gate. After silo startup, a dedicated request envelope creates the journal identity if it is absent, verifies the identity and the journal catalog, then opens that gate. Shutdown closes public and due scheduling first, keeps private journal routing alive and decorates only the manager's exact public Active lifecycle subscription. Its observer completes cleanup and joins `RequestWorkOwner` before grain deactivation. The start and every lifecycle property are forwarded unchanged; an unexpected descriptor, subscription or stage fails closed, no reserved lifecycle stage is repurposed and the receiver stays registered unchanged.

REQ-ORL-JOURNAL-STARTUP-015 / AC-ORL-JOURNAL-STARTUP-015: journal identity creation keeps one deterministic command ID for its whole startup lifetime. After an `UnknownWriteOutcome` it waits the configured poll interval and re-enters canonical verification under the same linked deadline and shutdown token: the protected-identity read comes first, and an existing identity is verified together with its complete journal catalog before admission opens. A lost response after a committed creation never produces a new command, identity, principal or storage authority. Credential, permission, corruption, format, quota and capability failures are not retried, no deadline is extended, and cancellation or terminal failure keeps admission closed. Automated regression: pending.

## jobs consumer and recovery

The first consumer hands already-due sagas to jobs, and the canonical Waiting saga record is the persistent pending-work intent. Due discovery uses the accepted background pattern: Orleans `[StatelessWorker]` grains accept due-saga events, buffer them in memory and, on an Orleans timer whose interval is a typed option, write the batch through the normal grain → ZoneTree owner path, scheduling at most one job attempt per due saga per cycle. No leadership check gates this work. The saga stays Waiting until expiry. A lost schedule acknowledgement may produce a duplicate job on a later cycle, without immediate unbounded retry, and strict journal quotas bound retained work and fail explicitly under pressure. snapshot compaction lets completed jobs shrink the journal, and due discovery recovers work after restart. Immediate future-deadline registration and single persisted job handles need a separate atomic wake-intent/uncertainty contract.

Job metadata contains only canonical IDs, revision and deadline: no roles, credentials, request envelopes, user JSON or timeout message content. Each schedule request supplies a fresh valid unsampled W3C trace parent and an empty trace state, independent of the ambient activity. In the pinned Orleans version an empty trace parent triggers ambient inheritance, so empty strings cannot opt out; the returned job must prove that caller trace state was not retained.

The execution `IDurableJobHandler` grain that receives saga expiry jobs keeps only invocation-local state, and its receiver extension may AlwaysInterleave. It reloads canonical saga and creator state and creates the existing creator-authorized expiry request through the connection grain's CQRS stream. Expected saga revision, phase/deadline checks and timeout-message identity guard the effect; stale, canceled, completed and revoked jobs have no effect. Unknown outcomes and required-copy unavailability are resolved only within an explicit bounded policy using the same stable command identity.

## Graph caller identity

Default-deny ManagedCode.Orleans.Graph rules and Orleans call tracking stay. The existing DirectedGraph/GrainTransitionManager descriptor is extended by copying every existing edge and adding the exact `RuntimeJournalClient` ReadCoreAsync → `IConnectionGrain.ExecuteStreamAsync` and SendCommandAsync → `IConnectionGrain.ExecuteStreamAsync` transitions, plus the job handler's `ExecuteJobAsync` → `IConnectionGrain.ExecuteStreamAsync` edge for its saga effect. JournaledStateManager runs a context-suppressed background loop, so `RuntimeJournalClient` establishes its provider caller identity through Graph's `RunWithCurrentCallerAsync` around the complete request-stream drain and restores prior context on success, error and cancellation. `JobGraphRegistration` uses the client's closed method identities instead of duplicated literals. No AllowAll, AnyMethod allowance, manager wildcard or replaced receiver extension is used, and no grain or Grain Service identity is impersonated.

## Requirements and acceptance

REQ-ORL-013 requires bounded journal-backed jobs whose state flows through the connection grain's CQRS path into the replicated ZoneTree owners, with owner-generation checks and creator-authorized idempotent saga expiry. AC-ORL-013 requires real canonical create/append/replace/read/reopen/delete, metadata CAS and same-owner updates, stale and recreated-handle failures, capacity exhaustion without partial writes, a complete catalog, identity and credential denial, unknown-outcome receipt resolution and actual job execution. Process restart and job-shard adoption, loss of a required write copy, creator revocation, schedule-acknowledgement uncertainty and a single timeout effect must pass through the Aspire replicated cluster with the real .NET SDK and official MCP client.
