# Resource retirement — D3

D3 prepares durable exact-lifetime effect exclusion through the existing native Orleans, RF3 journal and node-local ordered apply path. It implements neither public DROP nor physical cleanup. [D1 creation identity](ResourceLifetime.md), the prepared [D2 owner inventory](ResourceOwnerInventory.md) and [DROP dependencies](../RelationalStorage/DropTableDependencies.md) remain separate contracts. Resource names remain reusable with distinct D1 identities; no permanent name-only reservation is selected.

## Closed durable attempts and exact prepared operations

ResourceRetirementAttemptContextV1 has exactly one closed purpose. SealBarrier=1 carries the actual Retirement control and no Preparation/Receiver; OwnerReservation=2 carries the actual Preparation control plus its exact registered Receiver and no Retirement control. ResourceRetirementAttemptV1 replaces the unshipped Seal/Reservation-specific attempt DTOs. Its twelve fields retain AttemptId, bounded Ordinal, original ExpiresAt, inside-commit PrepareReceipt, Stage, actual source phase5 PrincipalId/PolicyEpoch, deterministic OriginalCommandId, optional OriginalFingerprint/TerminalReceipt and terminal Error/SafeDetail. Stages are Prepared=1, Failed=2, Expired=3 and Completed=4. Undefined values and mixed contexts refuse. State.SealAttempt retains its property name but uses the generic type; PreparationState.OwnerAttempts holds receiver-bound current source pointers. Every pointer/history read binds to the actual original phase5 source outcome.

PrepareAttempt=5 durably CASes the exact source context/current ordinal under fresh persisted administration. For Seal it follows every required owner fence receipt; for OwnerReservation it precedes any target issue. Bounded history and the deterministic original4/8 ID belong to the source, not a parallel target phase8 manager. Still-Prepared work does not advance merely because a coordinator times out, loses memory or observes expiry. A subsequent source phase5 requires the matching actual target Closed witness before recording the prior terminal transition and installing a new attempt. A completed reservation cannot be replaced. Original bodies/GUIDs and attempt expiry never renew through retry.

For OwnerReservation the sequence is source phase5 acknowledgment -> target factory issues one authenticated original8 -> target RF3 phase6 Persist acknowledges its full exact bytes -> submission of that same original8 -> source phase9 records its genuine owner receipt. The full ReplicatedOperation includes PayloadJson, NativePayload, authority/signature, principal, EvaluatedAt and ID. Recovery uses ReadResourceRetirementAttempt and ReadPreparedResourceRetirementOperation, not coordinator memory, log scans, reconstructed bodies or re-signing. A missing target prepared row remains UNKNOWN; it does not prove that an issue/submission failed or authorize the next source attempt. No full caller-supplied failed original or inferred GLOBAL-outcome history replaces canonical target body persistence.

PreparedOperation=6 has the closed actions Persist=1 and Close=2. They use distinct deterministic PreparedOperationCommandId values within the same attempt, so a retained successful Persist cannot prevent a subsequent Close. The prepared row has stages Persisted=1 and Closed=2. Phase6 success has only the PreparedOperation result arm. The actual phase6 ReceiptAuthority records its own persisted actor, policy epoch, fingerprint and evaluated time; PersistAuthority preserves the original Persist actor when a different current administrator closes it. These actors may differ from both source phase5 and original8. Target outcome checks use their actual subjects, never an inferred source principal.

Close carries no caller-provided Original. It reads the canonical target row and actual original outcome. A verified failed original can be closed with that error; a successful original cannot be closed as failure. Without a terminal original outcome, Close requires actual ordered target expiry. This includes never-issued work: a real target phase6 Close commits its receipt and Closed row before source advancement. Closed is permanent through this D3 stage and wins against delayed old Persist/original8. Missing row alone is never a terminal witness. Current authentication and exact stored source/context/receipt validation remain mandatory.

Final D2 inventory carries the actual source-issued Prepared Seal attempt in native Control field 8 and uses its OriginalCommandId as InventoryId. Ordinary active controls carry null. The Seal purpose uses the same generic source phase5 and target phase6 protocol at the source execution owner: capture final inventory, issue the full original4 once, persist it, then submit the exact original. Phase6 first validates the original source-local D2 cut. Seal permits only that certified single phase6 write: original StorePosition plus one, actual PersistReceipt applied index, and otherwise unchanged identity/read-generation/enrollment/topology. Extra intervening writes fail the attempt; there is no fabricated broad cut tolerance.

The exact prepared original4/8 retains its original EvaluatedAt through the narrow verified-original lane. The leader checks deadline using one actual native admission-clock observation before append; committed apply uses deterministic persisted clock and ordered Closed state, not independent per-replica wall clocks. The clock watermark remains its original maximum. Retained-outcome selection, fresh policy and actual target prepared-row validation precede the narrow clock exception. Ordinary commands keep their original clock rule.

Recoverable Seal validation retains the exact failed outcome/fingerprint and source Failed attempt while parent Retiring and every owner fence remain. Owner phase8 consumes the exact target-persisted original before its bounded native census or reservation effects; its source attempt is completed only by source phase9 with the genuine reservation receipt. Corruption and unsupported storage formats retain their original hard failures. Every context/body/result/history remains within original byte/count/transaction limits, and missing/unavailable state never becomes success.

## Phase order and linearization

The implementation prerequisites are D1 identity -> D2 authoritative inventory capability -> D3 durable retirement. Runtime phase order is different from a task-number order: PrepareRetirement -> for every registered group: source PrepareAttempt(OwnerReservation), once-issued original8, target PreparedOperation(Persist), exact ReserveOwner and source RecordReservation -> actual native movement settlement -> all-voter OwnerStatus -> Begin -> FenceOwner on every registered group -> RecordOwnerReceipt for every group -> PrepareAttempt(SealBarrier) -> final D2 inventory -> once-issued original4 -> PreparedOperation(Persist) -> exact SealBarrier. An earlier D2 Complete snapshot is historical observation, never a future admission fence.

PrepareRetirement first commits Preparing at the actual source control owner. In that SAME transaction it conservatively freezes physical owner registration and GLOBAL new native movement starts, matching the actual global native active-work snapshot, and captures the actual already accepted central parent/control identities, each full PartitionRef plus MoveId. It captures the initial directory and lifetime authority, not the final placement revision. D1 remains Active and ordinary authorized model writes/new logical partition bindings remain legal. This is movement admission, not D4 read/producer settlement.

Each ReserveOwner commits an immutable local reservation with its actual same-commit active move/import cohort. Its effective allowed drain cohort is the authenticated central accepted set union this exact local set. A move accepted at control before Preparing may have no target local stage yet: its later genuine target arrival retains the original source proof, control intent, grant, role and MAC verification. A GUID alone does not authorize a transfer. New ControlCheckpoint/ControlPrepare starts outside the reserved cohort refuse through the same canonical admission/apply path; already accepted native completion and abort paths remain available.

OwnerStatus carries a narrow actual native cut (node, incarnation, read generation, store position, applied index and catalog revision) and initialized actual Remaining identities. Empty Remaining is observed from native state, never a caller bool or inferred log absence. The status does not require D2 Proven, and unrelated business store-position advances do not invalidate it. Begin requires exact recorded reservations and actual authenticated statuses from every registered RF3 voter, then rechecks actual source-local settlement in its own ordered commit. Only then does it capture CURRENT placement/control and definition while preserving the exact old D1, transition to Retiring and proceed to deterministic owner fences. All source/owner acceptance predicates remain bounded.

A dynamic owner census may fail, but it does not create a second target attempt history. Source phase5 remains the owner-attempt authority; phase8 consumes only its exact target-persisted original. Pending or unknown recovery reads the stored attempt/body and retains original bytes and expiry. If no target body can be read, work stays UNKNOWN until an actual ordered target Close establishes terminal exclusion. A fresh recovery invocation does not resume cancelled original work or silently renew its deadline. Source phase9 binds the actual original fingerprint and reservation receipt, completing the corresponding source current pointer/history atomically.

Preparing counters/active indices are separate from Retiring. Snapshot replacement, archive reconciliation and blob incarnation rebind check both under their existing ownership. Source Begin removes its Preparing active index/count only while installing Retiring; an owner Fence does the same for its reservation while installing the exact-lifetime fence. Immutable history remains for original replay/recovery. A separate replacement-only prepared-target counter is installed on the first OwnerReservation-purpose phase6 Persist or Close, including never-issued Close. It is retained without D3 decrement and is checked by the existing snapshot/archive/blob replacement guards. It does not enter the Preparing source/owner active-index count or movement-cohort census, so it cannot fabricate an index/count mismatch or block ordinary business by itself. Timeout and cancellation retain durable Preparing, reservations and original attempts; they cannot claim Retiring or Complete.

Begin commits Retiring at the actual source journal/apply position, retains the complete definition/D1 pair, freezes the registered directory and placement witness, and denies new source effects for that exact lifetime. Begin alone does not make every remote owner retired. Every owner fence linearizes in its own original ordered journal commit. Lower committed/applying entries precede it; a later fence cannot leapfrog them. Later old-lifetime effects refuse on ALL that owner's atomic partitions, including a previously unseen partition.

The source records each canonical owner receipt and only then admits final retiring inventory. D2 is still conservative may-contain: B-only writes may conservatively add A membership in a shared domain even while A effects are fenced. That is extra potential coverage, not permission to delete a cohabited partition. Capture the final inventory after the operation's own phase/receipt writes and all required owner-wide fences; do not demand that an earlier D2 StorePosition cut survive those intentional writes.

SealBarrier is the durable global effect-exclusion acknowledgment after every required RF3 owner fence, complete final all-voter inventory and exact source revalidation. D4 separately owns existing read cuts, pins, accepted lower-order work and joined background settlement. D5 separately owns bounded exact-lifetime cleanup. D6/D7 own terminal removal/recreate and public/API SQL lowering. No D3 success claims that old pins have closed or data has been erased.

## Bounds, cancellation and errors

Reuse the original ReadExecutionBudget, token, absolute expiry, DatabaseLimits and canonical command transaction bounds. Required directory, receipts, all-node cuts, final inventory, phase body and typed result must fit original native/read/output/transaction limits. Oversized work refuses before phase effects; there is no truncated success or raised limit. Inventory reads use BudgetExceeded; original command expansion retains ResourceExhausted and its original failed-outcome/reset boundary.

Malformed phase/scope/enum identities yield Validation. Fresh admission retains Unauthenticated/PermissionDenied. Initial complete source absence or absent exact recovery state yields NotFound. Contradictory persisted state/proof/receipt yields Corruption. Changed old lifetime/policy/admission yields TokenInvalidated. Actual owner/directory/placement mismatch yields OwnershipLost. New effects on the current Retiring lifetime yield Conflict with fixed detail `The resource lifetime is retiring.` Unknown/unavailable/unsettled required state yields RecoveryRequired or the original transport failure, never Complete. Original cancellation/deadline errors propagate and settle the original work.

Cancellation or a failed/unknown attempt never removes committed Retiring, installed fences or receipts. A fresh authorized recovery attempt can resume the same durable intent and deterministic phase IDs with its own bounded caller budget. It cannot renew a still-running original attempt, roll back an acknowledged owner fence or weaken original errors.
