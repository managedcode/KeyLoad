Why an AI-native database

Agents shouldn't need a dozen databases.

One agent step reads a task, looks up a customer, searches similar cases, updates a knowledge graph and stores a file. Today those steps usually span several databases, each with its own client, credentials and failure modes.

The stitched stack

  • Postgres records
  • Vector DB embeddings
  • Redis · RabbitMQ tasks
  • S3 files
  • Kafka events
  • Graph DB relationships
  • Time-series DB metrics
  • Glue code sync jobs

Seven permission models, seven sets of credentials, copies kept in sync by hand and no transaction that spans them.

One AI-native database

  • One reference Any record can point to any other through canonical entity references.
  • One permission check Keys and policies live in the database, so an agent gets exactly what you grant.
  • One atomic write A document, its event, a graph edge and the next task in the same partition commit together.
  • One way in SQL, the built-in MCP server and the .NET SDK reach the same operations.

Why we think this is the future: agents don't think in tables, queues or buckets. When every shape of data lives in one database, an agent step should become one authorized operation instead of a distributed saga held together by glue code. Today its writes within one partition already commit atomically; leased receives, blob uploads and cross-partition work are still separate steps. Nobody should have to run a stack of databases just to let agents get work done.

Data that works together

Connected data. One request.

Tables, collections and queues organize one database. An agent can follow entity references across models and write the result through the same persisted permissions.

  1. 01

    Queue to knowledge graph

    Read ready messages, resolve their linked entities and write knowledge-graph relationships inside the database.

  2. 02

    Graph to queued actions

    Follow visible relationships to enqueue actions carrying canonical entity references.

  3. 03

    One authorized atomic command

    Every source and target must live in the same atomic partition and transaction domain, so the whole command succeeds or rolls back together. Reading a queue into the graph does not lease or ACK its messages. Blobs remain part of the same database, but use their separate upload and publication operations.

The current composition API runs through SQL CALL, the .NET SDK and the official MCP server. KeyLoad is a development preview: full declarative SQL, the native SQL-client protocol and cross-partition composition are still in development, and production guarantees remain under qualification.

Anatomy of one agent call

Two ways in. One atomic commit.

The MCP server and the .NET SDK reach the same engine, the same persisted permissions and the same transaction rule.

  1. 01

    The agent calls a tool

    An MCP tool call or SDK command arrives with a credential the database verifies against its own stored policy.

  2. 02

    A grain takes the request

    Every request runs in its own Orleans grain, which invokes only the database grains it needs.

  3. 03

    The partition commits atomically

    The document, its event and the follow-up job are written together, or none of them are.

  4. 04

    Three replicas store it

    A majority of the three node-local replicas persists the commit before the call returns.

Built on .NET 10 and Orleans

A grain per request. Storage that stays home.

Orleans gives every request its own grain and finds the right partition through a distributed grain directory. Grains can move between nodes to balance load; the data does not. ZoneTree files, write-ahead logs and the ordered commit gate stay with each node's PartitionHost, so moving a grain never copies storage.

Activation-migration qualification is still in progress.

Why .NET, Orleans and ZoneTree

One runtime. No glue in between.

The database, its cluster and its storage run in one .NET process per node. Orleans moves the routing; ZoneTree keeps the data in place.

.NET 10

A fast, memory-efficient runtime

Spans, pooled buffers and hardware intrinsics keep hot paths lean; SIMD work is measured before any speed claim. One language from server to SDK, CLI and tests.

dotnet/runtime ↗ Orleans

A cluster runtime proven in production

Virtual actors from Microsoft Research that have powered Halo's cloud services. Membership and failure detection are built in; KeyLoad adds a grain per request and turns on the experimental distributed directory and activation repartitioning, still being qualified.

Methodology

How we measure.

Read the benchmark methodology ↗
  1. 01

    Shared inputs

    A seeded corpus fixes document bytes, vectors, graph edges and request schedules. Workload conditions and corpus hash travel with each report.

  2. 02

    Real command paths

    Clients call real services. Setup, warmup and correctness checks are outside the timer; queue cycles include enqueue, receive and ACK.

  3. 03

    Correctness first

    Writes are read back, graph results match a reference traversal, and queue completion rejects missing, duplicate or wrong-payload messages.
